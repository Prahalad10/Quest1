    NOTE THE COST: this is a policy limit, not a promise of speed. At the

    Shorter queries match almost anywhere; the timestamp would be meaningless.


--- 2. MATCHING THRESHOLDS  (rapidfuzz partial_ratio, 0-100) --------------------
MATCH_THRESHOLD       70    QUEST1_MATCH_THRESHOLD
    Below this = no_match.  *** VALIDATED -- DO NOT LOWER WITHOUT RE-TESTING ***
        TRUE  matches  n=83   min 71.4   median 100
        FALSE matches  n=184  median 53.7  max 68.0
        false >=70: 0/184     false >=65: 3/184     false >=60: 17/184
    The false sample uses real phrases from OTHER videos, not gibberish
    (gibberish tops out ~59 and makes 70 look safer than it is).
    65 was rejected: it admits false positives, and the one missed true match
    scored 62.5 so 65 would not have recovered it either.
CONFIDENT_THRESHOLD   88    QUEST1_CONFIDENT_THRESHOLD
    >=88 = "confident", else "ambiguous". Validated: every result >=88 landed on
    the correct timestamp; both mislocated results scored below (76.7, 82.1).
AMBIGUITY_MARGIN      5     QUEST1_AMBIGUITY_MARGIN
    Runner-up within this margin -> downgrade to ambiguous. Stops a coin-flip
    between repeated lines being reported as fact.
MAX_OCCURRENCES       20    QUEST1_MAX_OCCURRENCES
NEAR_MISS_THRESHOLD   45    QUEST1_NEAR_MISS_THRESHOLD
NEAR_MISS_COUNT       3     QUEST1_NEAR_MISS_COUNT
    Shown only when nothing clears MATCH_THRESHOLD. Kept low deliberately: on a
    short video every near miss scores 48-55, and a higher floor would show
    nothing at all. Labelled "closest lines", never presented as an answer.
Bands: BAND_CONFIDENT / BAND_AMBIGUOUS / BAND_NO_MATCH
       = "confident" / "ambiguous" / "no_match"
    (renaming these breaks the frontend).
Enforced in app/core/matching.py.


--- 3. ASR ---------------------------------------------------------------------
ASR_MODEL          small   QUEST1_ASR_MODEL      tiny/base/small/medium/large-v3
ASR_DEVICE         cpu     QUEST1_ASR_DEVICE     "cuda" if a GPU exists
ASR_COMPUTE_TYPE   int8    QUEST1_ASR_COMPUTE_TYPE   float16 on GPU
ASR_BEAM_SIZE      1       QUEST1_ASR_BEAM_SIZE
    *** THE BIGGEST SPEED LEVER IN THE PIPELINE. *** 90s of dense speech,
    small/int8/8 threads, changing only this:
        beam=5  76.4s  1.18x realtime      beam=1  25.9s  3.47x realtime  (2.95x)
    Beam search runs the decoder once per beam. The accuracy it buys does not
    matter here: matching is fuzzy at MATCH_THRESHOLD=70, so a transcript must
    be wrong by far more than a beam-1/beam-5 disagreement before a line stops
    being found. Set to 5 to trade the speed back.
ASR_LANGUAGE       None    QUEST1_ASR_LANGUAGE   None = auto-detect
ASR_VAD_FILTER     True    QUEST1_ASR_VAD        off = slower + hallucinations
ASR_PROGRESS_INTERVAL_SECONDS  2.0   QUEST1_ASR_PROGRESS_INTERVAL
    Heartbeat interval. Needed because faster-whisper only yields a segment once
    it has finished decoding it (30-40s apart on long video), so a bar driven by
    segment arrivals alone freezes -- that was "stuck at 80%". The heartbeat
    interpolates from observed rate, clamped so it cannot overstate progress,
    and reports indeterminate before the first segment rather than inventing a
    number.  (app/core/asr.py, _Heartbeat)
First use downloads the model to ~/.cache/huggingface.
If a phrase is not found, check what the model HEARD (python -m app.core.asr
<wav>) before touching MATCH_THRESHOLD.


--- 4. AUDIO -------------------------------------------------------------------
AUDIO_SAMPLE_RATE  16000  / AUDIO_CHANNELS 1     Do not change; Whisper resamples
                                                 to this internally anyway.
AUDIO_BYTES_PER_SECOND      32000 (derived)      expected wav size = duration x this
AUDIO_DURATION_TOLERANCE_SECONDS 2 / AUDIO_DURATION_TOLERANCE_RATIO 0.05
    A wav shorter than the video by more than max(2s, 5%) = truncated fetch ->
    raises. Silent truncation would transcribe half the video and report
    "not found" for everything in the missing half.
AUDIO_USE_CHUNKED_DOWNLOAD  True   QUEST1_AUDIO_CHUNKED ("0" = ffmpeg streaming)
AUDIO_HTTP_CHUNK_SIZE       10MB   QUEST1_AUDIO_CHUNK_SIZE
AUDIO_CONCURRENT_FRAGMENTS  4      QUEST1_AUDIO_CONCURRENT_FRAGMENTS
    *** Largest perf fix in the project. *** Same bytes, same URL, 797s video:
        ffmpeg sequential read  399.1s      yt-dlp chunked ranges  8.7s   (30x)
    YouTube throttles one long sequential read to ~30 KB/s but serves chunked
    ranged requests at ~2 MB/s. Does NOT download the video -- audio only, and
    audio was always written to disk regardless. Frames still read remotely.


--- 4b. AUDIO TRACK SELECTION  (multi-language uploads) -------------------------
AUDIO_TRACK_LANGUAGE  None  QUEST1_AUDIO_LANGUAGE
    None = the ORIGINAL track. Set a code ("hi", "es") to transcribe that dub
    on purpose; honoured only if a track in that language exists.

*** THIS WAS A SILENT WRONG-ANSWER BUG, NOT A CRASH. ***
    A MrBeast upload carried 14 audio tracks: one English original
    (language_preference=10) and 13 dubs (-1), several dubs at a HIGHER bitrate
    than the original. select_audio_format ranked on bitrate alone and chose the
    ARABIC dub. The video transcribed cleanly into Arabic (lang=ar, p=0.99), and
    every English query returned "not found" with no error anywhere -- nothing
    had failed, we had simply transcribed the wrong soundtrack.

    Selection order is now: requested language > language_preference > bitrate.
    See _track_rank / select_audio_format in app/core/resolve.py.

TWO CACHE RULES THIS DEPENDS ON -- both were needed, one was not enough:
  1. data/{media_key}/audio.meta.json records WHICH track the wav came from.
     audio.wav used to be reused on existence alone, so a wav built from a dub
     survived the fix. A mismatch now forces a re-fetch.
     The signed URL is deliberately NOT part of the signature: it rotates, and
     including it would re-download the audio on every run.
  2. Re-fetching audio DELETES transcript.json and index.json. Without this the
     English audio was fetched correctly and the Arabic transcript was then
     served from cache -- still the wrong answer, still no error. The transcript
     is a pure function of the audio; invalidating the input must invalidate
     everything derived from it.

COUNT LANGUAGES, NOT FORMATS. ResolvedMedia.audio_track_count uses
count_audio_languages(). YouTube publishes the same audio in several codecs
(139/140/249/250/251), so counting audio-only FORMATS returns 5+ for an ordinary
single-language video. A first version did that, judged every cached wav stale,
and re-transcribed videos that were already correct.

--- 4c. FLAKY HOSTS AND NON-YOUTUBE SOURCES  (ok.ru) ----------------------------
RESOLVE_MAX_ATTEMPTS          8   QUEST1_RESOLVE_ATTEMPTS
RESOLVE_RETRY_BACKOFF_SECONDS 2   QUEST1_RESOLVE_BACKOFF   (linear: N x backoff)
RESOLVE_HTTP_RETRIES          3   QUEST1_RESOLVE_HTTP_RETRIES  (yt-dlp internal)

ok.ru resets a share of connections (WinError 10054). The SAME url fails, then
succeeds, then fails, with nothing changed. Observed: one run failed 4 straight
attempts; the next succeeded on attempt 2. Hence 8, not 4.
    Only transport-shaped failures retry. A private/removed video, DRM, or a
    404 is a stable answer and raises immediately -- see is_transient_error()
    in app/core/resolve.py.
    CAUTION on the marker list: a bare "age" matched "unable to download
    webPAGE" and made the one error this exists to retry look permanent. Keep
    every marker specific enough that it cannot match inside another word.

RETRY BOTH PLACES THAT EXTRACT. resolve() and _download_audio() BOTH run the
yt-dlp extractor, so retrying only in resolve() moved the failure one stage
later instead of fixing it. Shared helper: resolve.retry_transient().

RESUMABLE DOWNLOADS. _download_audio used to delete every audio_src.* leftover
before starting, which restarted a 125 MB fetch from zero on each interruption.
ok.ru serves this film as ~1500 DASH fragments and takes ~12 min. Now .part /
.ytdl / .part-FragN are KEPT so yt-dlp resumes, and the finished-file selection
excludes them so a truncated file can never be transcoded.

UNKNOWN CODEC FIELDS BROKE THREE SEPARATE SELECTORS. ok.ru reports its
progressive streams with vcodec=None AND acodec=None, and reports no height or
bitrate either. Each selector had to be taught the same lesson:

  _has_video()      required a known vcodec, so the only seekable stream was
                    discarded -> "No plain-HTTP video format available" for a
                    video whose MP4 was right there.
  _may_have_audio() (new) some ok.ru videos have NO audio-only track at all --
                    only HLS plus unknown-codec progressive MP4s. Requiring a
                    known acodec rejected every candidate -> "No audio stream
                    found in any available format. Cannot transcribe silent
                    media." about a film that talks throughout.
  select_video_format() ranked on (height, tbr). With both unknown every format
                    tied, max() returned the FIRST, and yt-dlp lists formats
                    worst-first -- so frames came from `mobile` while `hd` sat
                    unused. An index tiebreak now picks the better stream.
                    Verified: 960x720 frame instead of mobile-resolution.

A container with both codec fields unset is assumed to carry what its extension
implies. Audio-only streams always report a real acodec, so they cannot be
mistaken for video. If the guess is ever wrong, ffmpeg fails at `-map a:0` with
a clear message -- better than refusing a usable video up front.

PROGRESSIVE AUDIO IS THE ONE PATH THAT FETCHES VIDEO BYTES. When a host offers
no audio-only track, the SMALLEST progressive format is downloaded and its audio
extracted (45 MB for a 54-min episode). ensure_audio warns when this happens.
The warning used to test `vcodec not in (None,"none")`, which missed exactly
this case and stayed silent; it now keys off StreamChoice.is_audio_only, decided
at selection time where the full format dict is still available.

SSL: probe_http_ranges() fails on ok.ru with CERTIFICATE_VERIFY_FAILED. It does
NOT matter -- the range probe was removed as unused, and ffmpeg
uses its own TLS stack and reads the stream fine. Verified: probe returned
852x480 @ 29.97fps CFR, and ranged frame extraction succeeded at 2min / 30min /
60min into the film.

--- 5. FRAME EXTRACTION --------------------------------------------------------
FRAME_PREROLL_SECONDS            5     QUEST1_FRAME_PREROLL
    Coarse -ss lands this far before target so the decoder has a keyframe; the
    remainder is a fine -ss after -i. Too small = miss the keyframe.
FRAME_URL_EXPIRY_MARGIN_SECONDS  60    QUEST1_FRAME_EXPIRY_MARGIN
FRAME_TIMEOUT_SECONDS            180   QUEST1_FRAME_TIMEOUT
Frame number = floor(timestamp x fps). FLOOR, not round: the frame on screen at
t is the one whose interval contains t.
VFR (r_frame_rate != avg_frame_rate by >1%): frame_number is null + a note. The
IMAGE is still correct; only the integer is unavailable. Never guess it.


--- 6. CACHING -----------------------------------------------------------------
INDEX_VERSION  2  (not env-overridable)
    v2 = ASR_BEAM_SIZE default 5 -> 1. Every v1 index on disk is ignored.
    *** BUMP to invalidate every transcript index on disk. *** Required after
    ANY change to normalize.py rules or the word/segment schema -- a stale index
    yields wrong char offsets and therefore wrong timestamps, silently.
RESOLVE_CACHE_TTL_SECONDS 3600  QUEST1_RESOLVE_CACHE_TTL
    Fallback only; the signed URL's own expire= governs when present.

  data/_resolve/{sha256(url)[:24]}.json     keyed by URL
  data/{media_key}/audio.wav | probe.json | transcript.json | index.json
  data/{media_key}/frames/frame_<ms>.png    keyed by timestamp
  Matching is never cached (milliseconds, query-dependent).

media_key = {extractor}-{video_id}-{sha256(extractor:id)[:10]}
    Derived from extractor+id ONLY, never the stream URL. Signed URLs rotate on
    every resolve, so a URL-derived key would miss the cache every time and
    re-run ASR on every query.

Jobs are in-process (app/jobs.py): they do NOT survive a restart and do NOT work
across multiple uvicorn workers. Swap InMemoryJobStore before scaling past one.
ffmpeg remote inputs always get: -reconnect 1 -reconnect_streamed 1
                                 -reconnect_delay_max 5
Host MUST honour HTTP Range (verified at resolve time; YouTube returns 206).
Format selection: audio = highest-bitrate audio-only (vcodec=none); video =
video-only (DASH) preferred, protocol must be http(s) -- HLS/DASH manifests are
rejected because they are not seekable byte streams.

--- 9. NORMALIZATION  (app/core/normalize.py) ----------------------------------
Same function at index time AND query time. *** ANY CHANGE => BUMP INDEX_VERSION ***
  1. NFKC  2. curly quotes -> ASCII  3. hyphen/dash/slash/underscore -> space
  4. drop everything not letter/digit/space  5. collapse whitespace
  "Don't -- you DARE!" -> "dont you dare"    "well-known" -> "well known"
Accents preserved. Digits stay digits: "1975" will NOT match spoken "nineteen
seventy five" (known limitation).


--- 10. EXIT CODES / STATUS ----------------------------------------------------
CLI: 0 found | 1 no match (near misses printed) | 2 error
     Distinct so a script can tell "not in this video" from "broken".
status: "found" | "not_found"   (errors raise, never a status)
Refused at resolve (UnsupportedMediaError): playlists, live, upcoming,

--- 10a. RESOLVE CACHE MUST RE-DERIVE ITS KEY ----------------------------------
_cached_resolve_is_usable() re-computes media_key from the cached extractor +
video_id and rejects the entry if it differs.

WHY: everything under data/ is addressed by media_key, and the resolve cache
STORES that key. A brief change to compute_media_key left entries on disk
holding the old key, so resolve returned a hit pointing at a directory that did
not exist -- the pipeline then re-ran a full ASR pass with a perfectly good
cache sitting beside it, reporting a cache HIT the whole time. Re-deriving the
key costs one hash and makes that class of failure impossible.

--- 11. PERFORMANCE  (all measured -- do not re-litigate) -----------------------
THE COST MODEL: ASR dominates, and it scales with SPEECH, not with duration.
VAD skips silence, so a sparse film is far cheaper per minute than a dense
interview. Measured end-to-end, cold, first index:

    length  content            audio+probe   ASR      total    x realtime
      19s   vlog clip                ~6s      ~8s     15.9s      1.2x
     3.1m   podcast                  ~9s      70s     85.0s      2.2x
     5.0m   explainer               ~10s     120s    134.8s      2.2x
     8.8m   short film              ~10s     115s    129.5s      4.1x
    11.9m   interview (dense)       ~10s     233s    247.3s      2.9x
    95.7m   feature film (sparse)    62s     666s    ~740s       7.8x  (ASR alone 8.6x)

    The 19s clip is 1.2x only because ~12s of it is fixed overhead (resolve,
    model load) that does not grow with length. Overhead stops mattering above
    about a minute.

    Dense speech runs ~2.2-2.9x realtime; sparse ~8.6x. A 90-minute film is
    ~11-12 min cold, NOT the ~35 min the old baseline implied.

WARM IS THE NORMAL CASE. Once a video is indexed, a new query costs:
    0.3s   answer + a frame already extracted
    9.5s   answer + a NEW frame pulled remotely from 90 min into a 1080p stream
Only the FIRST query on a video pays for ASR.

WHAT WORKED
  * beam_size 5 -> 1.  2.95x, the single biggest win. See section 3.
  * yt-dlp chunked ranged audio fetch instead of ffmpeg streaming. 30x on the
    audio stage. See section 4.

WHAT DID NOT WORK, AND WHY (both premises measured false)
  * Coarse/fine two-tier decoding (cheap model locates, accurate model refines).
    tiny is only 1.30x faster than small despite being 6x smaller, and dropping
    word alignment saves ~19%. Removed.
  * Chunked multi-process decoding (removed, see section 10b). Thread scaling at
    beam=5 predicted 2.5x:
        1 thread 0.81x | 2 threads 1.10x | 4 threads 1.30x | 8 threads 1.18x
    -- a single stream barely uses the machine, so four workers should win.
    END TO END IT DELIVERED 1.03-1.11x. At beam=1 the work is memory-BANDWIDTH
    bound, not compute bound, so extra processes contend for one memory bus.
    Deleted rather than left switched off.
  * A smaller model is NOT reliably faster: base/beam1 measured 92.7s against
    small/beam1's 25.9s on identical audio. Decode cost tracks TOKENS EMITTED,
    and small models emit repetition loops. Do not assume tiny/base are quicker
    -- measure.

THE REMAINING GAP
    "Any 90-minute video answered in 1-2 minutes, cold" is NOT reachable here.
    It needs ~48x realtime; the best measured is 8.6x on sparse audio and ~2.5x
    on dense. Closing it needs a hosted ASR API or a CUDA GPU (this machine
    reports 0 CUDA devices), not more CPU restructuring.
    What IS delivered: any video up to 2h is accepted; ~10 min of speech indexes
    inside 3 min cold; every subsequent query on it answers in under 10s.

MACHINE: 4 physical cores / 8 logical, 7.8 GB RAM, no CUDA. Every number above
is from this machine; they are not portable.
